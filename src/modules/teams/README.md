# Teams and performance (ALSMV2-1102 / ALSMV2-1186)

Updated priorities: team mutations now use an exact shared MongoDB transaction for business state and central audit. Transaction-capable MongoDB is required; standalone writes fail closed. This supersedes the separate-write descriptions retained below from the first implementation. See [current atomic mutation contract](../../../docs/operations/TEAM_ATOMIC_MUTATIONS_20261017.md). Stable IDs, revision checks and exact-assignment revocation preconditions remain mandatory.

Organization-owned SALES and CONVERSION teams have explicitly persisted members, managers and project/staff assignments. No membership or management scope is inferred from organization membership, global roles or job creators. No existing data is backfilled.

`POST /api/v1/teams` creates a team with `expectedRevision: 0` and a client-generated, stable 24-hex `creationId`; `PUT /api/v1/teams/:teamId` replaces its explicit memberships/assignments using the exact current revision. Both require an active organization OWNER/ADMIN **and** the existing `users.manage` RBAC permission. No permissions or grants are seeded. Only active members of that exact organization can be appointed; viewers cannot manage. Team kind is immutable. Lists return only teams explicitly managed by the caller, selected by `?kind=SALES|CONVERSION` and optional existing `x-organization-id` context.

Schema: `teams` owns organization, kind, name, member IDs, manager IDs, project assignments, revision and retained change attribution. Project assignees must be team members and projects must be active in that organization. Changes use compare-and-set revision checks; complete actor-attributed snapshots are retained atomically in the team document. Central audit has a pre-mutation request event and a post-mutation outcome event. Central audit and the business mutation are separate writes: a post-write audit outage can yield an error after persistence; reload the revision before retrying. No transaction/rollback guarantee is claimed.

State ownership and Mongoose queries stay in infrastructure; application orchestration uses repository/public domain ports. Root AppModule composes the feature with existing organizations/users/RBAC/audit/project dependencies. The active demo branch is not the full protected AUTH-H1 security branch and does not enable support impersonation.

## Reporting and assignments

- `GET /api/v1/teams/:teamId/administration`: inspect membership/assignments and current revision, with the same restricted administration checks as writes.
- `GET /api/v1/teams/:teamId/performance?days=7|30`: exact SALES manager scope, actual active organization/team member roster and unavailable leadCount/conversionRate/revenueGenerated objects. No `value` is supplied for missing data. No lead/contract lifecycle or verified converted-to-customer status exists in this backend. Quote requests are not assigned leads, and invoice/payment customer IDs are not salesperson attribution. The approved `converted leads / assigned leads * 100` formula remains unchanged, but is not calculated without these sources; no made-up status or zero-denominator result is returned.
- `POST /api/v1/teams/:teamId/job-assignments`: restricted administrator supplies `{ assignmentId, jobId, memberId }`, retaining the same client-generated 24-hex assignment ID across retries. Job and project must exist in this organization; the active staff member must have both explicit team membership and explicit project assignment. A manager cannot self-assign by virtue of reporting access.
- `GET /api/v1/teams/:teamId/job-assignments`: restricted administrator inspects current assignments.
- `DELETE /api/v1/teams/:teamId/job-assignments/:jobId?assignmentId=:exactAssignmentId`: restricted administrator explicitly revokes, retaining original assignment and revocation actor/time. Reassignment requires revocation then a new record, never silently overwrites attribution.
- `GET /api/v1/teams/:teamId/workload?days=7|30`: exact CONVERSION manager/Team Lead scope, current active member breakdown and totals derived from actual jobs selected through a scoped conversion read port. No source/result paths, legacy code or other teams' job details are returned.

Both reports use **rolling elapsed UTC days**, with server-anchored half-open `[start,end)` boundaries returned in the payload. Workload selects **job.createdAt in that period**, current explicit job/project/member assignment, and currently persisted status. It is a current status view of the selected created-job cohort, not historical backlog, terminal-event throughput or event-time staff attribution. One distinct job counts once, including after automatic attempts or manual retry; execution generations are not KPI units. Assigned Jobs includes all selected statuses; Processing/Completed/Failed count the exact corresponding statuses (DEAD is not silently relabeled FAILED). Queued, cancelled and dead jobs can therefore be included in Assigned without appearing in those three subsets. No trends/capacity/alerts or automatic polling are claimed.

Only explicitly assigned jobs in active assigned projects and current active organization/team staff memberships are counted. Existing legacy jobs are not attributed from `createdBy`; zero means the explicitly assigned cohort is empty, not that the entire organization's unassigned workload is zero. Removed members/project assignments are excluded immediately on subsequent reads. Assignment records remain retained; administrators must revoke obsolete job assignments explicitly. The report rechecks actor, team revision, organization membership and assignment set before returning; concurrent changes reject the report for refresh. Status reads across projects are not a single transactional snapshot.

`team_job_assignments` stores organization/team/project/job/member and original assigning actor/time plus optional revocation actor/time. The named partial unique index `one_active_team_job_assignment` on organizationId/jobId with revokedAt=null ensures one active assignment per job across teams. Assignment writes fail closed if that index is absent/mismatched. Provision the declared indexes in a reviewed deployment before use; no production schema migration, seeding or backfill is performed by this task. Assignment state retains attribution atomically; central audit request/outcome appends are separate writes with the same post-write ambiguity described above.

The organization-owned team model and 7/30 filters implement the minimum approval. Separate internal scopes, first-assignment sales counting, closed-opportunity win rate, recognition-ledger accounting and historical generation KPIs from the earlier unapproved proposal are not activated. Sales integration remains a data dependency; the new administration/reporting APIs are real but do not make that missing CRM/accounting system exist.

## Operational retry contract

Create IDs are permanent MongoDB `_id` fences, not optional request labels. POST without a creation/assignment ID is rejected. Replaying creation with the same actor and normalized original payload returns the existing team's current state with `replayedCreation: true`; it never resets later edits. Reusing an ID for different input or another actor/organization conflicts. Assignment replay returns the original retained record with `replayed: true` and `revokedAt`, even when revoked and replaced. A new ID represents a new explicit intent, never a transport retry. Retain these IDs and complete request payloads in the administration client before sending. Existing records need no migration. Do not delete retained teams, initial change snapshots, or assignment rows to clear retry fences.

DELETE requires the exact assignment ID from administration GET, so a delayed retry cannot revoke a replacement. `GET /api/v1/teams/:teamId/job-assignments/:assignmentId` lets the same authorized administrators reconcile retained active or revoked records. Ordinary members and managers without administration authority cannot inspect them. PUT still requires the exact current revision; after an uncertain PUT, inspect the administration record before deciding on another edit.

Mutation errors distinguish request-audit rejection (`TEAM_AUDIT_UNAVAILABLE`), unknown database outcome (`TEAM_MUTATION_OUTCOME_UNCONFIRMED`) and known persistence followed by completion-audit failure (`TEAM_MUTATION_COMMITTED_AUDIT_PENDING`). Through the existing API exception filter, outcome fields are in `details[0]` (`resourceId`, optional `revision`, `mutationCommitted`, `retrySafe: false`). Clients must not automatically retry these mutations, mint fresh IDs on error, or advance expected revisions. No `Retry-After` or automatic retry is provided. Central audit remains non-atomic; request events can exist without mutations, completion events can be absent, and deliberate same-ID reconciliation adds a reconciliation event rather than claiming a new assignment. A replay does not repair the missing historical audit event. See [development setup and incident procedure](../../../docs/operations/TEAM_PERFORMANCE_READINESS_20261017.md).
