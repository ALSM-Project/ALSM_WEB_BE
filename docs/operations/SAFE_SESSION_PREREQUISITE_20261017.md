# ALSMV2-1050: independently safe current-session prerequisite

Team administration, reporting, assignment administration and the new Sales workflow require both a valid JWT and a currently persisted session bound to its authenticated account. The server takes `sid` only from the verified JWT context, resolves the account and authoritative sessions through existing public repository ports, and rejects missing/mismatched/revoked/expired sessions, inactive accounts and required password changes. Repository failures deny access with `SESSION_ASSURANCE_UNAVAILABLE`; no token-only fallback is used. Normal login already issues the persisted session ID as `sid`, so no token issuance, JWT guard, secret or MFA implementation is replaced.

This is an ordinary live-session check at request admission. It does **not** provide command-bound step-up MFA, atomic proof consumption, replay protection, authentication-generation fencing, trusted personnel governance, support approvals or cross-instance containment. It does not claim to serialize session revocation with the subsequent business transaction. No customer identity, impersonation token, operational support session or impersonation route is created. ALSMV2-1050 operational impersonation remains blocked until all approved governance/session/MFA/approval/containment prerequisites are verified together.

The protected security branch and frozen security/evaluation artifacts remain untouched. Tests cover active sessions, missing/foreign/revoked/expired sessions, inactive accounts, password-change requirements and storage failure. Real HTTP/Mongo tests demonstrate that revoking a session denies a still-valid signed JWT and that borrowing another account's session ID cannot authorize administration. Existing business authorization remains additional: organization role, existing RBAC permission and explicit team management/membership are never inferred from session validity.
