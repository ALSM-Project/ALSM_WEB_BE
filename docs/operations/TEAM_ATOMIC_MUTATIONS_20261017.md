# Updated priorities: atomic team administration

This supersedes the separate-write audit limitation in the earlier 17 October operational report. Existing local history and frozen security/benchmark artifacts are unchanged. No converter investigation or engine execution is part of this work.

Team creation/replacement and job assignment/revocation now execute requested audit, business write and outcome audit in the same MongoDB transaction. Infrastructure creates explicit session-bound team, assignment and audit participants from the same connection. The application unit-of-work port has no Mongoose types. Transaction options match the established security pattern: snapshot reads, primary routing and majority writes. There is no ordinary append or standalone-write fallback. The protected security branch is inspected read-only and remains untouched; this does not activate security governance or impersonation.

An audit failure aborts the business change as well as both audit events. A conflict aborts the request event too. The failure response is `ATOMIC_MUTATION_ABORTED`, with `details[0].mutationCommitted:false` and `retrySafe:false`. A commit error labeled `UnknownTransactionCommitResult` instead returns `TEAM_MUTATION_OUTCOME_UNCONFIRMED` and `mutationCommitted:'unknown'`; it never claims rollback. Stable client creation/assignment IDs and revision checks remain required for reconciliation. Revocation still requires the exact retained assignment ID, so an old retry cannot revoke its replacement.

MongoDB **must support transactions** (replica set or mongos). Standalone deployments reject team mutations with `MONGO_TRANSACTIONS_REQUIRED` before the unit of work executes. Reads remain available. No existing database, application container or production topology is changed automatically. Operators must arrange a reviewed transaction-capable deployment before using writes; do not weaken this precondition. Existing named uniqueness indexes still must be provisioned. Duplicate-key races receive at most one whole-transaction restart using the original identity, never an in-transaction read after an aborted insert. Normal driver transient-transaction retries do not repeat external effects: the callback contains only transaction-bound MongoDB writes.

Verification uses a new disposable `mongo:8` single-node replica set, container `alsm-priorities-20261017-mongo-rs`, label `alsm.owner=priorities-20261017`, sole binding `127.0.0.1:27127`, set `alsmPriorities`. The existing original application and standalone development database containers are untouched. The opt-in Team HTTP test verifies this exact ownership and uses unique `alsm_team_http_<run>` databases with guarded cleanup. It covers rollback when outcome audit fails after team creation, assignment creation and revocation, concurrent creation/assignment conflicts, retained history, scoped authorization, report periods and delayed DELETE retries. Runner unit tests cover standalone rejection and unknown commit outcomes. Setup commands and exact results are in the final updated-priorities report/evidence.

This fixes state/audit atomicity for these team operations. It does not imply serializable global identity governance, command-bound MFA, protected principal assurance, atomic support approval consumption or cross-instance impersonation containment. Operational impersonation remains disabled.
